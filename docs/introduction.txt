========================================================================
WebServer 项目介绍
========================================================================

一、项目目标
------------------------------------------------------------------------
从零实现一个基于 Reactor 模式的多线程 HTTP 服务器。

整体采用「主从 Reactor」架构：
    - 主 Reactor（main reactor）只负责 accept 新连接
    - 子 Reactor（sub reactor）负责已建立连接的读写事件
    - 连接的读写全部在「该连接所属的子线程」中完成，避免加锁

分层设计，自下而上共三层：

    base/   基础设施层：线程封装、时间戳、日志（同步 + 异步）、同步原语
    net/    TCP 网络层：事件循环、Channel、连接管理、线程池、定时器、缓冲区
    http/   HTTP 协议层：报文解析、响应构造、连接驱动

依赖方向严格「自下而上」：
    http 依赖 net，net 依赖 base，反向不依赖。
    下层通过「回调」把控制权交给上层（控制反转），
    因此 net 层不知道 http 层的存在，可以复用于其他协议。

三、核心组件说明
------------------------------------------------------------------------

1. EventLoop（事件循环）
   每个线程一个 EventLoop，内部持有 Epoller、一个 wakeup_channel_
   和一个 timer_queue_。
   - Loop()            主循环：epoll_wait → 分发事件 → 执行待办任务
   - RunInLoop(func)   若在所属线程则直接执行，否则投递到队列
   - QueueInLoop(func) 把任务放入待办队列，并唤醒 eventfd
   - DoPendingFunctors() 执行待办队列中的任务
   - RunAfter / RunEvery / CancelTimer  转发给 TimerQueue

   待办队列 + eventfd 唤醒，是「跨线程投递任务」的关键机制。

2. Channel（事件封装）
   把一个 fd 和它关心的事件、回调绑定在一起。
   - EnableRead / EnableWrite / DisableRead / DisableWrite  修改监听事件
   - HandleEvent()  根据 ready_events_ 分发到读/写回调
   - Tie(ptr)       绑定一个 weak_ptr，用于延迟销毁

   Tie 存的是 weak_ptr，不增加引用计数；
   只在 HandleEvent 期间 lock() 提升为 shared_ptr，
   保证回调执行期间对象不被析构。

3. Buffer（读写缓冲区）
   底层为 std::vector<char>，配一对读/写索引，构成经典三段式布局：

   +-------------------+------------------+------------------+
   | prependable bytes |  readable bytes  |  writable bytes  |
   |                   |     Content      |                  |
   +-------------------+------------------+------------------+
                       |                  |
                   read_index_       write_index_

   - prependable  已消费但未回收的空间，用于 O(1) 前置协议头
   - readable     已接收但未被上层消费的有效数据
   - writable     尾部空闲空间，用于追加新数据

   索引语义：
   - 初始 read_index_ = write_index_ = kCheapPrepend（8 字节）
   - 写入时 write_index_ 右移，读取时 read_index_ 右移
   - ReadableBytes() = write_index_ - read_index_
   - Retrieve() 只移动索引，不搬数据、不释放内存

   关键接口：
   - Append(data, len)         追加数据，空间不足先 EnsureWritableBytes
   - Prepend(data, len)        在 readable 段前插入，仅前移 read_index_
   - EnsureWritableBytes(len)  保证尾部有 len 字节可写
   - ExpandSpace(len)          扩容：真扩容 resize / 伪扩容搬移回收
   - ReadFd(fd, &savedErrno)   readv 分散读，栈上 64KB 备用缓冲兜底
   - WriteFd(fd, &savedErrno)  write 一次，成功后自动 Retrieve
   - Retrieve / RetrieveAll / RetrieveAsString / RetrieveUntil
   - Peek / FindCRLF           零拷贝读取视图与 CRLF 定位

   扩容策略（ExpandSpace）：
   - 真扩容：writable + prependable < len + kCheapPrepend 时 resize，
     把 vector 扩到 write_index_ + len
   - 伪扩容：首尾空闲拼起来够用，则把 readable 段搬到 kCheapPrepend，
     回收 prependable 空间，避免 vector 无限增长

   ReadFd 的两段式读：
   用 iovec[2] 同时指向「缓冲区尾部空闲区」和「栈上 64KB extraBuf」，
   一次 readv 就能把数据读满。若读入量超过 writable，
   说明 extraBuf 已被使用，把 write_index_ 推到末尾后 Append 补齐。
   这样避免了「先探测可读字节数再扩容」的额外系统调用。

   为什么用 vector<char> 而不是 std::string：
   - char 语义明确，不隐含「以 \0 结尾」的假设
   - vector 的 resize 语义清晰，不会因 SSO 造成小缓冲区地址不稳定
   - 与 readv/writev 的裸内存视图天然契合

4. TcpConnection（连接对象）
   - ConnectionEstablish()  Tie + EnableRead + 触发连接回调
   - HandleMessage()        Read + 状态校验 + 重置空闲定时器 + 触发消息回调
   - HandleClose()          DisableRead + 撤销空闲定时器 + 触发关闭回调（幂等）
   - ForceClose()           HandleClose + shutdown(SHUT_WR)，服务器主动关闭
   - ConnectionDestruct()   DeleteChannel，从 epoll 摘除 fd
   - ReadNonBlocking()      循环 ReadFd 直到 EAGAIN，累积到 input_buffer_
   - WriteNonBlocking()     循环 WriteFd 直到写完或 EAGAIN

   双缓冲区：
   - input_buffer_   读缓冲，ReadFd 写入，由 on_message_ 以 Buffer* 交给上层消费
   - output_buffer_  写缓冲，Send 追加，WriteNonBlocking 消费

   Send 接口（两个重载，共用同一份写路径）：
   - Send(const std::string& msg)
   - Send(const char* msg, int len)   额外校验 len < 0 与 msg == nullptr
   两者都是「Append 到 output_buffer_ → Write()」，
   Write() 在 WriteNonBlocking 之后重新校验连接状态，
   若本轮写操作已触发 HandleClose，则不再操作 channel，
   避免把已关闭的连接重新注册 EPOLLOUT。

   写事件注册：
   Write() 在 WriteNonBlocking 返回后检查 output_buffer_ 是否仍有残留，
   有则 EnableWrite（首次进入时置 writing_ = true），
   无则 DisableWrite。EAGAIN 时残留数据由 EPOLLOUT 可写事件驱动
   HandleWrite → Write 继续发送，因此大响应不会被丢弃。

   空闲超时接口：
   - EnableIdleTimeout(sec) 建连后注册一次性定时器，到期回调 ForceClose
   - ResetIdleTimer()       每次读到数据后「取消 + 重发」，实现滑动续期
   - CancelIdleTimer()      关闭时撤销，解除定时器持有的 shared_ptr

   状态机（ConnectionState）：
   - Invalid        初始/非法
   - Connected      正常读写
   - DisConnected   已进入关闭流程
   Read / Write / Send 入口均以 Connected 为前置条件，
   底层 I/O 出错后 HandleClose 会立即把状态切到 DisConnected，
   调用方返回后必须重新校验状态，这是本类的一条硬约束。

5. TcpServer（服务器）
   - HandleNewConnection(fd) 创建 TcpConnection，分配到子 Reactor，
                             注入三个回调，RunInLoop 到子线程注册空闲超时
   - HandleClose(conn)       先转发上层 on_close_，再投递 HandleCloseInLoop
   - HandleCloseInLoop(conn) 在 main reactor 中删表，再投递析构任务
   - set_conn_timeout_(sec)  配置超时秒数，默认 60s，0 表示不启用

   连接表 connections_map_ 的增删都在 main reactor 线程中完成。

6. HttpContext（报文解析）
   采用「有限状态机 + 循环」的方式解析：
   保持一个 while 循环，持续判断单步解析的状态，来切换当前解析状态。
   例如：如果解析请求行的结果为 kOk，则切换到 kExpectHeaderLine 状态，
   下一次循环就会进入解析首部行的函数中。

   状态流转：
       kExpectRequestLine → kExpectHeaderLine → kExpectBody → kGotAll

   单步解析结果有三种：
       kOk       本步完成，切换状态
       kNeedMore 数据不完整，返回等待更多数据（半包）
       kError    报文非法

   解析结果（ParseResult）同样有三种：
       kGotAll   完整解析出一个请求
       kNeedMore 数据不够，等下次
       kError    报文错误

7. HttpConnection（连接驱动）
   - OnMessage(Buffer* buf)  while 循环 ParseRequest，处理粘包与半包
   - HandleRequest           构造 HttpResponse，交业务回调填装
   - SendResponse            ToString(true) 序列化后经 TcpConnection::Send 发出

   数据流：TcpConnection 的 input_buffer_ 以 Buffer* 传入，
   HttpContext 直接在 Buffer 上做零拷贝解析（Peek / FindCRLF / RetrieveUntil），
   只有被消费的字节才推进 read_index_，未解析完的半包留在缓冲区里等下次。

   状态标记：
   - should_close_     报文错误或需关闭时置位，循环结束后统一 HandleClose
   - keepalive_count_  预留字段，长连接计数（当前未启用）

   当前连接语义：默认长连接。
   SendResponse 固定以 ToString(true) 序列化，响应头始终为
   Connection: keep-alive；连接的生命周期由空闲超时兜底，而非请求计数。

8. HttpResponse（响应构造）
   ToString(bool keep_alive) 是序列化核心，由框架接管两个关键首部：
   - Content-Length  由 body_ 长度计算，过滤业务层写入的值
   - Connection      由 keep_alive 参数决定，过滤业务层写入的值
   204 No Content 按语义不输出 Content-Length。

9. TimerQueue（定时器队列）
   EventLoop 持有 TimerQueue，TimerQueue 持有 timerfd_ 和对应的 Channel。
   timerfd 到期变为可读，经 Channel 回调进入 HandleRead，
   从而把「定时事件」统一成「IO 事件」，复用同一套 epoll 分发机制。

   对外接口（由 EventLoop 转发）：
   - RunAfter(delay, cb)       delay 秒后执行一次，返回 timer_id
   - RunEvery(interval, cb)    每 interval 秒执行一次，返回 timer_id
   - CancelTimer(id)           取消指定定时器

   内部数据结构：
   - timer_set_    std::set<TimerEntry>，按 (time, id) 升序，队首即最早到期
   - id_to_time_   std::unordered_map<id, TimeStamp>，供 CancelTimer 快速定位
   - next_id_      自增 id 分配器

   TimerEntry 的排序规则：time 相同则比 id。
   这既保证同一时刻多个定时器的顺序稳定，
   也让 set::find 能用 {id, nullptr, time, 0} 构造的查找键精确命中。

   关键设计：
   - timerfd 使用 CLOCK_MONOTONIC，不受 NTP 校时 / 手动改时间影响
   - 只有新定时器成为队首时才 ResetTimerfd，避免无谓的系统调用
   - 周期定时器在 HandleRead 中回插，而非使用 timerfd 的 it_interval

10. Logger（日志前端）
    使用方式：
        LOG_INFO << "fd=" << fd;
    输出格式：
        [INFO] 2026-11-05 14:37:35.312882 536289 tcp_connection.cc-152: fd=8
        （等级、时间、线程 tid、文件-行号、正文）

    等级：kDebug / kInfo / kWarn / kError / kFatal，默认输出 kDebug 及以上。

    组件分工：
    - SourceFile        从 __FILE__ 截取文件名，避免打印完整路径
    - FixedBuffer       栈上 4000 字节缓冲区，避免每条日志一次堆分配
    - LogStream         重载 operator<<，把字符串/整数/TimeStamp 追加进缓冲区
    - Logger            构造时拼前缀，析构时把整行交给 AsyncLogging::Append

    为什么用宏：
    宏展开能拿到调用点的 __FILE__ 和 __LINE__；
    若写成函数调用，拿到的只会是 logger.cc 自己的文件名和行号。
    宏体为 if(ShouldLog(level)) Logger(...).stream()，
    等级不满足时连 Logger 对象都不构造，零开销。

    线程安全：
    每条日志的缓冲区是 Logger 的成员，位于各自线程的栈上，天然隔离；
    跨线程的唯一交汇点是 AsyncLogging::Append，由一把互斥锁保护。
    因此前端无需为「行不交错」做额外处理。

    可替换输出：
    - SetLogFile(basename)  指定落盘文件，空串表示 stdout
    - SetInterval(sec)      指定后端最长刷新间隔，默认 3s
    两者须在第一条日志之前调用（异步实例在首次打印时惰性构造）。

    LOG_FATAL 语义：
    绕过异步队列，直接 fwrite + fflush 后 abort()，用于不可恢复错误（如 errif）。
    走同步路径是为了保证崩溃前的最后一条日志一定落盘。

    已知限制：
    - 单条日志超过 4000 字节时，超出部分被静默丢弃（FixedBuffer 空间不足直接返回）
    - minLevel 与配置项无原子保护，约定在启动阶段配置，运行期不切换

11. AsyncLogging（异步日志后端）
    动机：同步日志的两个阻塞点都在业务线程上——
    fwrite 内部有 FILE* 锁，多线程并发打日志会排队等锁；
    缓冲区满时 fwrite 触发 write，write 是阻塞的，直接拖慢业务线程。
    日志量一大，业务延迟就被日志吃掉。

    拆分方式：
    业务线程只做「格式化 + 内存拷贝」，把整行交给 Append；
    真正的 fwrite / fflush 由唯一的后端线程完成。

    三个核心机制：
    1) 前端缓冲区
       每个业务线程在栈上拼好一行，Append 时整行 memcpy 进
       curr_buffer_（4MB 的 FixedBuffer），不做任何 IO。
    2) 双缓冲交换
       前端持有 curr_buffer_ / next_buffer_，后端持有 buffer1 / buffer2。
       前端缓冲写满时，把 curr_buffer_ 推入 buffers_ 队列，
       立刻换上 next_buffer_ 继续写，不等待后端。
       后端被唤醒后，用 buffersToWrite.swap(buffers_) 一次性取走整批，
       swap 是 O(1)，交换期间前端持锁时间极短。
    3) 唤醒机制
       前端缓冲满时 notify_one；后端在 buffers_ 为空时
       以 flush_interval_ 为上限 wait_for，兼顾「有数据立刻写」与
       「低频小流量也不至于长期不落盘」。

    缓冲对象回收：
    后端写完一批后，把多余缓冲 resize 掉，只留两个回填 buffer1 / buffer2，
    下一轮再交给前端当 next_buffer_，避免每轮都 new 4MB。

    退出排空：
    Stop() 置 running_ = false 并 notify，后端跳出循环后
    还会把 curr_buffer_ 里残留的日志补写一遍再退出，
    保证「进程正常结束时不丢最后一批日志」。

    代价：
    - 进程崩溃（abort / 段错误 / kill -9）时，队列中未写出的日志会丢失
    - 多一个后端线程和若干 4MB 缓冲的常驻内存

12. Latch（倒计数闩锁）
    用途：让「创建线程的一方」等到「新线程真正跑起来」再继续。
    AsyncLogging::Start 中 thread_ 已创建，但后端线程可能还没进入
    ThreadFunc，此时若主线程立刻 Append，虽然逻辑上安全（有锁），
    但 flush_interval_ 等成员的可见性依赖闩锁建立的同步关系。

    - Wait()       阻塞直到 count_ == 0
    - CountDown()  计数减一，减到 0 时 notify_all
    后端线程进入 ThreadFunc 后第一件事就是 CountDown，
    主线程的 Wait 随即返回，Start 才算真正完成。


四、请求处理流程（一次完整 GET）
------------------------------------------------------------------------
 客户端
   │  1. TCP 三次握手
   ▼
 主 Reactor ── accept ──► TcpServer::HandleNewConnection
   │                          │
   │                          ├─ next_loop() 选一个子 Reactor
   │                          ├─ 创建 TcpConnection（绑定 sub_reactor_）
   │                          ├─ 注入 close/message/connect 回调
   │                          ├─ RunInLoop 到子线程注册空闲超时
   │                          ├─ connections_map_[fd] = conn
   │                          └─ ConnectionEstablish（Tie + EnableRead）
   ▼
 子 Reactor ── epoll 可读 ──► TcpConnection::HandleMessage
   │                          │
   │                          ├─ Read() → ReadNonBlocking → input_buffer_
   │                          ├─ 状态校验（DisConnected 则直接返回）
   │                          ├─ ResetIdleTimer() 滑动续期
   │                          └─ on_message_(self, &input_buffer_)
   ▼
 HttpServer::OnMessage
   │
   ├─ 加锁查 http_conns_，取出 HttpConnection 的 shared_ptr 副本
   │  （副本保证锁外使用期间对象不被 OnClose 析构）
   ▼
 HttpConnection::OnMessage(Buffer* buf)
   │
   ├─ while 循环调用 context_.ParseRequest(buf)   ← 处理粘包
   │     ├─ kGotAll   → HandleRequest + Reset，继续循环
   │     ├─ kNeedMore → break，等下次数据          ← 处理半包
   │     └─ kError    → should_close_ = true，break
   │
   └─ HandleRequest → 业务回调填装 resp → SendResponse
                           │
                           └─ conn_->Send(ToString(true))
                                  │
                                  ├─ output_buffer_.Append(...)
                                  └─ Write()
                                        ├─ WriteNonBlocking()  循环 write
                                        └─ 有残留 → EnableWrite；无残留 → DisableWrite

 默认长连接：响应头为 Connection: keep-alive，连接不随响应结束而关闭，
 客户端可继续在同一连接上发送下一个请求。
 连接终止有两种途径：
 1) 客户端主动关闭：服务器 read 返回 0，进入关闭流程；
 2) 空闲超时：客户端 conn_timeout_ 秒内无数据，服务器 ForceClose 主动断开。


五、连接管理
------------------------------------------------------------------------
新建连接：见 docs/map/newConnection.md
关闭连接：见 docs/map/deleteConnection.md
整体类图：见 docs/map/architecture.md

关闭链路要点：
  TcpConnection::HandleClose
      → 置 DisConnected + DisableRead + DisableWrite（若在写）
      → CancelIdleTimer              （撤销定时器，解除强引用）
      → TcpServer::HandleClose       （转发上层 + 投递到 main）
      → HttpServer::OnClose          （删除 http_conns_ 中的条目）
      → TcpServer::HandleCloseInLoop （删除 connections_map_）
      → TcpConnection::ConnectionDestruct（DeleteChannel，摘除 fd）
      → 引用计数归零，TcpConnection 析构

  ForceClose 在 HandleClose 之后追加 shutdown(fd, SHUT_WR)：
  关闭「本端 → 对端」的写方向并发出 FIN，让对端立即感知服务器不再发送数据。
  相比直接 close()，它不会因接收缓冲区尚有未读数据而立刻回 RST，
  对端若配合关闭，即可走完干净的四次挥手；
  且 shutdown 不释放 fd，fd 的释放仍由 ConnectionDestruct 统一接管。

  注意：SHUT_WR 之后若对端仍继续发数据，内核会回 RST。
  这在超时关闭场景下是预期行为，明确告知对端连接已作废。
  且 HandleClose 中已 DisableRead、连接随后被析构，
  本端不再消费任何入站数据，不存在「半关闭后还能继续读」的语义。

  两次「延迟」的原因：
  1) 不能在 HandleEvent 的调用栈中析构对象，否则返回后访问已释放内存；
  2) 连接表的增删必须在 main reactor 线程中，保证线程安全。


六、空闲超时设计
------------------------------------------------------------------------
1. 为什么用定时器而不是 SO_RCVTIMEO
   SO_RCVTIMEO 只能让 read 超时返回，无法表达「空闲多久后关闭连接」，
   也无法在关闭时执行完整的 HandleClose 链路。
   用 RunAfter 注册一次性定时器，到期回调直接走 ForceClose，
   复用已有的关闭流程，不新增任何状态机分支。

2. 滑动续期：取消 + 重发
   ResetIdleTimer() 先 CancelTimer(idle_timer_id_)，再 RunAfter 重新注册。
   这样每次收到数据，超时窗口都从「现在」重新起算，
   语义等价于「连接空闲超过 conn_timeout_ 秒则关闭」。
   长连接下，只要客户端持续发请求，连接就不会被超时回收。

3. 定时器持有 shared_ptr 的隐患与解除
   RunAfter 的回调用 std::bind 捕获了 shared_from_this()，
   定时器条目本身持有一个 TcpConnection 的强引用。
   若连接已关闭而定时器未撤销，对象会一直存活到定时器到期。
   因此 HandleClose 中必须 CancelIdleTimer()，
   让引用计数及时归零，ConnectionDestruct 才能正常析构。

4. 线程归属
   EnableIdleTimeout 通过 RunInLoop 投递到连接所属的子 Reactor 执行，
   保证 timer_queue_ 的读写只发生在该 EventLoop 线程内，无需加锁。
   每个 EventLoop 持有自己的 TimerQueue 与 timerfd，
   因此 ForceClose 也必然在该连接所属线程执行。

5. 参数保护
   EnableIdleTimeout 对 seconds <= 0 直接返回，
   避免「超时为 0」导致所有连接建连后立刻被 ForceClose。
   idle_timer_id_ != -1 时也直接返回，防止重复注册。

6. 已知限制
   - 超时精度受 timerfd 与 TimeStamp 差值计算影响，为毫秒级
   - 周期定时器在自己的回调里 CancelTimer 自己会失效：
     此时该条目已被 GetExpired 移出 set，CancelTimer 找不到它，
     回调返回后又会把它回插，相当于「取消被忽略」。
   - ResetTimerfd 用 realtime 差值计算间隔，
     若 NTP 恰好在两次 ResetTimerfd 之间跳变，算出的间隔会失真。
     窗口极短（微秒级），实践中可接受。


七、设计要点
------------------------------------------------------------------------
1. 控制反转（IoC）
   回调的精髓是控制反转：
   上层负责策略（决定做什么），下层负责行为（决定何时触发）。
   控制流在注册时从上往下，事件与请求数据在触发时从下往上，
   响应数据则从上往下写回。

2. 依赖倒置
   下层依赖抽象（std::function 回调），上层注入具体策略。
   例如 TcpConnection 只依赖 on_message_ 这个抽象，
   具体调用由上层注册决定，因此 net 层不依赖 http 层。

3. 单一职责
   HttpServer      只负责连接管理
   HttpConnection  只负责协议流程控制
   HttpContext     只负责报文解析
   TcpConnection   只负责连接生命周期与读写
   Buffer          只负责字节的存取与索引管理，不理解协议
   TimerQueue      只负责定时调度，不关心回调内容
   Logger          只负责格式化，不关心落盘时机
   AsyncLogging    只负责落盘，不关心日志内容

4. 延迟销毁
   通过「待办队列 + weak_ptr 保护 + 引用计数」三者配合，
   保证对象在所有回调执行完毕后才析构，避免悬空指针。
   定时器持有强引用时，必须靠 CancelTimer 主动解除。

5. 事件抽象的统一
   timerfd 把时间维度的事件映射成 fd 的可读事件，
   使 EventLoop 只需处理「fd 就绪」这一种抽象。
   新增定时能力不需要改动 Epoller / Channel / Loop 的任何代码，
   只增加一个 Channel 注册即可。

6. 框架接管关键首部
   Content-Length 与 Connection 由 HttpResponse 统一生成，
   业务回调即使写入也会被过滤。
   避免「长度与正文不一致」和「连接语义前后矛盾」两类错误。

7. 日志的「快慢分离」
   把日志拆成「格式化（业务线程）」与「落盘（后端线程）」两段，
   中间用缓冲队列解耦。
   业务线程的日志开销被压缩为一次 memcpy + 一次可能的 notify，
   与磁盘 IO 彻底脱钩。

8. 缓冲区与协议解耦
   Buffer 只提供「字节容器 + 索引视图」，不包含任何协议语义；
   HTTP 的半包/粘包处理完全由 HttpContext 在 Buffer 视图上完成。
   因此 Buffer 可直接复用于其他协议，只需换一个解析器。

9. 状态前置校验
   TcpConnection 的 Read / Write / Send 入口都以 Connected 为前置条件，
   且底层 I/O 函数（ReadNonBlocking / WriteNonBlocking）出错时会主动
   切换到 DisConnected。因此「调用底层 I/O 后必须重新校验状态」
   是本类的硬约束，避免对已关闭连接继续操作 channel。

结论：
1) 峰值约 58 万 QPS（12 线程 / 500 连接 / 30s，最高 581,700，
   中位数 558,437），连续 3 次离散度约 ±3%，测量稳定。
2) 压测线程数从 4 提到 8，QPS 从 16.9 万跃升到 47.5 万（2.8 倍）。
   4 线程时压测端只占 4 个核，服务端 16 个 sub reactor 跑不满，
   此时瓶颈完全在压测端而非服务端。
3) 线程数从 8 增到 16，QPS 仅从 47.5 万涨到 54.7 万（+15%），
   而 P99 从 4.34ms 涨到 7.98ms（+84%）。说明 8 线程以上时
   压测端与服务端开始争抢同一批 CPU，继续加线程只增加排队延迟，
   不增加吞吐。这是「同机压测」的固有上限。
4) 连接数从 500 增到 800（16 线程），QPS 反而从 547,257 微降到
   542,023，平均延迟从 1.38ms 涨到 1.87ms，P50 从 519us 涨到 990us。
   符合「服务端已饱和、新增连接排队」特征，500 连接为当前配置拐点。
5) P50 延迟稳定在 363~387us，而平均延迟为 1.03~1.12ms。
   两者相差约 3 倍，说明延迟分布存在长尾（P99 6~6.5ms），
   平均值被少量慢请求拉高。P50 更能反映典型请求的真实体验。
6) 压测期间服务端日志共 2906 条，全部为
   tcp_connection.cc-171 的 "Connection reset by peer"，
   时间戳集中在每轮压测结束的瞬间（如 17:53:15、17:56:06），
   属于压测端主动断连产生的 RST，不是服务端缺陷。
   已确认无其他类型错误。
7) 压测后 RSS 稳定在 24.6 MB，fd 数量 74，无异常增长。
8) 服务端空闲时 CPU 占用为 0（/proc/pid/stat 的 utime+stime
   在 5 秒窗口内采样，增量为 0 tick），无空转。

说明：本组数据只反映「固定正文、单路由、无文件 IO」下的框架开销，
不能直接与静态文件服务器对比。真实业务中 JSON 序列化、DB 查询、
模板渲染等开销会远大于本组的正文拷贝，QPS 会显著低于上述数值。

环境干扰说明：
1) 电源策略影响极大。省电模式下同一配置（12 线程 / 500 连接）
   实测仅 26 万 QPS，性能模式下为 55~58 万，相差约一倍。
   压测前必须确认电源策略，否则数据不可比。
2) WSL2 的 load average 统计失真，实测出现过 load = 34.81 但
   CPU 空闲率 98%、运行队列只有 1 个任务的情况，因此本组数据
   不以 load average 作为环境判据，改用 /proc/stat 的 CPU 空闲率
   与 /proc/pid/stat 的进程 CPU tick 直接采样。
